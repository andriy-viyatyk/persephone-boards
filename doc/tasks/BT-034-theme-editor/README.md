## Goal

Replace the scaffolded `theme-editor` starter with an offline Theme Editor board that creates and edits Persephone custom themes through the narrow `persephone.themes.*` bridge. Let users derive a complete palette from three base colors, adjust any derived CSS or Monaco color, preview changes live, and save, organize, import, and export named themes.

## Background

- The product decisions and scope are in [EPIC-123, especially Decisions and US-1640](../../../../persephone/doc/epics/EPIC-123.md). Persephone owns derivation, storage, and bridge behavior; this board owns the editing UI. Built-in themes are read-only starting points. The base colors are background, text, and accent, with optional link/error/warning/success values. A custom theme stores base intent and overrides, not a frozen full palette.
- The board already exists at `boards/theme-editor/`, scaffolded with `index.html`, `app.js`, `board-base.css`, `scripts/hello.js`, `board-manifest.json`, and the generic board authoring guide in `CLAUDE.md`. This task replaces the demo UI and identity metadata; it does not create another board folder.
- `C:/projects/persephone/src/renderer/api/themes.ts` and `src/renderer/api/types/themes.d.ts` define the app API and plain JSON types. `src/board-shim.ts`, `src/renderer/api/mcp/board-call-command.ts`, and `assets/guides/boards.md` confirm the board namespace and transport contract. For this board, all methods are asynchronous, including `current()`; `get(id)` returns `null` when absent. `themes: true` grants only the themes bridge, not `appScripting`; the exact denial without the grant is `permission-denied: "themes" is not enabled in board-manifest.json`.
- Verified bridge calls and shapes:
  - `list(): Promise<ThemeDefinition[]>`, `get(id): Promise<ThemeDefinition | null>`, `current(): Promise<ThemeDefinition>`.
  - `derive(base, isDark?): Promise<ThemeDefinition>` where `base` has required `background`, `text`, `accent`, optional `link`, `error`, `warning`, `success`, and `isDark` is `boolean | null` when supplied.
  - `file(id): Promise<CustomThemeFile | null>` returns the stored file for a saved custom theme, preserving only optional base keys the author set and `isDark: null` for Auto; built-ins and unknown ids return `null`. Use this to edit, revert, and export a saved custom theme without reconstructing its intent from a derived definition.
  - `contrast(input): Promise<ContrastReport>` accepts a `ThemeDefinition`, `CustomThemeFile`, or `ThemeDraft`; the report is keyed by pair name and each entry is `{ ratio: number, meetsAA: boolean }`.
  - `fork(id): Promise<ThemeDraft>` returns an id-less draft. It preserves the selected definition by extracting base colors and differences from derivation; the returned name has `" copy"` appended.
  - `save(draft): Promise<CustomThemeFile>` creates a theme and returns the generated `custom-*` id, or replaces an existing custom theme only when the draft has its existing `id`. It does not select the saved theme or end a preview.
  - `rename(id, name): Promise<CustomThemeFile>`, `delete(id): Promise<void>`, `apply(id): Promise<void>`, `preview(draft): Promise<ThemeDefinition>`, `endPreview(): Promise<void>`.
  - `file(id)` is also declared on `app.themes`; the board call returns plain JSON through the asynchronous bridge.
- `src/renderer/theme/theme-color-vars.ts` is the authoritative ordered set of 77 CSS color variables. `src/renderer/theme/custom-theme.ts` derives each variable, routes `monaco:<key>` overrides, and computes contrast reports. There are seven editable Monaco color keys: `editor.background`, `menu.background`, `menu.foreground`, `menu.selectionBackground`, `menu.selectionForeground`, `menu.separatorBackground`, and `menu.border`.
- Preview changes are in-memory and window-local. The bridge guide specifies that closing, reloading, or navigating away from the requesting frame ends its preview only if a later preview or selection has not replaced it. `persephone.onThemeChange(cb)` fires immediately and on each active palette revision, including changes to a preview. The custom-theme directory watcher reloads the registry in each renderer; registry refresh publishes a theme revision even if the active id is unchanged.
- Board authoring constraints are in `boards/theme-editor/CLAUDE.md` (the copied generic guide): the board is a plain HTML/CSS/JS iframe app, `board-base.css` supplies the `--p-*` theme contract, and remote scripts/styles/fetch are blocked by CSP (`connect-src 'self'`). Keep it offline and use `--p-*` values for its own chrome. Native `window.alert/confirm/prompt` must not be used; use a `<dialog>` for destructive confirmations.
- Repo precedent: `boards/chess/` and `boards/agent-log-viewer/` use plain JS, `board-base.css` linked first, standalone `styles.css`, `icon.svg`, `screenshot.png`, metadata/version fields, and a one-line-per-change `WHATS-NEW.md`. The boards repo requires a bare screenshot filename in the manifest and a 1120×700 screenshot of the app content below the page-tab strip, with real but non-personal sample content and a target under ~300 KB.

## Concerns / Open Questions

- **Browser file transfer needs live verification.** The board guide documents `connect-src 'self'` and permission-scoped bridge file methods but does not establish Blob download / file-input behavior in the board iframe. `src/main/download-service.ts` hooks session `will-download`, so a Blob link is expected to pass through Persephone's download handling; the user's live verification decides whether both transfer flows work. If transfer is blocked, record the exact behavior; do not add a `fileSystem` fallback.
- **Dirty drafts versus external updates.** The bridge offers no dedicated custom-theme-list event. `onThemeChange` receives registry revisions because reloads publish the active palette again, and it also fires for preview/apply. The board must distinguish refresh/invalidation from draft replacement and avoid erasing unsaved work. A dedicated event would be a Persephone-side gap if the revision signal changes.
- **Explicit preview ownership is not exposed.** `endPreview()` has no board/frame token; the bridge only applies ownership checks to its automatic frame cleanup. `current()` can be compared with this board's last preview, but identical preview definitions cannot identify their owner. Verify explicit Revert behavior with the bridge owner; do not invent a bridge member.
- **Import identity is deliberately new.** The import flow strips the imported id and calls `save()` with an id-less draft, creating a new theme. Import-as-replace is outside this behavior and would need an explicit mapping choice.
- **Contrast badges are measurements, not enforcement.** The verified report returns `ratio` and `meetsAA`; it does not alter base inputs or override values. Base colors can intentionally fail AA, so display the result without blocking save.
- **Preview is window-local.** The bridge previews in the renderer window containing the board. Applying a saved theme persists its id and other windows receive normal setting propagation; unsaved preview is not cross-window.
