# BT-049: Add the Codex Engine to Claude Agent

## Goal

Add Codex as a second engine behind the existing `agent.session` v1 provider-adapter boundary, using the user's installed `codex app-server` over JSON-RPC on stdio. Keep the existing Claude Agent board identity and Claude behavior; let users choose an engine through provider descriptions and capabilities.

## Background

- Persephone's [EPIC-131](C:/projects/persephone/doc/epics/EPIC-131.md), Phase 1, and [CLI research](C:/projects/persephone/doc/epics/EPIC-131-cli-research.md), sections 7.2 and 8.2, decide on `codex app-server`, not `@openai/codex-sdk`: the SDK wrapper is for `codex exec --json` and does not provide the required streaming and approval round-trip.
- **Protocol baseline verified while writing this plan:** installed CLI reports `codex-cli 0.163.0`. `codex app-server generate-ts --experimental --out <scratch>` and `generate-json-schema --experimental --out <scratch>` both succeeded into `%TEMP%\bt049-codex-protocol-0.163.0`; no generated protocol artifacts belong in the board. The CLI marks app-server experimental, so implementation must check the installed version before starting and regenerate/inspect the installed CLI's types before relying on protocol names. The protocol method/notification names in this plan are from those generated 0.163.0 bindings, not memory or the research file.
- Generated 0.163.0 bindings define client requests `thread/start`, `thread/resume`, `thread/list`, `thread/read`, `turn/start`, `turn/interrupt`, and `model/list`. Relevant notifications include `thread/started`, `turn/started`, `turn/completed`, `item/started`, `item/completed`, `item/agentMessage/delta`, `item/reasoning/textDelta`, `item/reasoning/summaryTextDelta`, `item/commandExecution/outputDelta`, `item/fileChange/outputDelta`, and `thread/tokenUsage/updated`. The generated `ServerRequest` union includes `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, `item/tool/requestUserInput`, `mcpServer/elicitation/request`, and legacy `execCommandApproval` / `applyPatchApproval`. Recheck these names and payloads against the CLI actually installed when implementation begins.
- Codex model records from `model/list` expose `id`, `displayName`, `description`, `supportedReasoningEfforts`, `defaultReasoningEffort`, and `isDefault`. `thread/tokenUsage/updated` contains `total`, `last`, and `modelContextWindow`; set `tokenUsage` and `contextUsage` capabilities true and normalize token/context status fields from it. Codex usage has no cost, budget, or native max-turn setting. The shared host enforces `open.limits.maxAgentSteps` only when a cross-board caller supplies it; local page opens send no limits and must not acquire a new default cap.
- Codex's per-thread `developerInstructions` parameter is present on generated `thread/start` and `thread/resume` types. The research records it as additive and placed before `AGENTS.md`; do not replace Codex's built-in instructions or repository `AGENTS.md` chain.
- The service currently defaults missing provider ids to Claude, registers only `claude`, issues and revokes a private Persephone MCP endpoint per session, and has shared policy/approval/process/session helpers. The Claude adapter currently owns much of `startSession` setup, `makePreamble`, file-based `instructionsFile` / `readInstructions` / `manageInstructions`, and `watchFor`; BT-048's review deferred the generic portions for this multi-provider task. Preserve the current file-backed Instructions dialog and user edits while moving shared storage and request handling into `service.mjs`.
- The UI already keeps `description` per provider id and stores provider ids on live views and session rows. It has one model chip/list and its new-session flow applies a selected model to the current provider. It currently makes an unqualified `describe` request for the default provider and does not present an engine picker. Plan a provider model catalog, group model choices by provider description, and retain the chosen opaque provider id with the new-session view. Provider ids are only routing keys; UI visibility and behavior branch on capabilities and description data, never vendor ids or names.
- `session-list` currently gets its rows through the selected adapter; the app already keys session views by `{provider,id}` and reads `sessions[].provider`. The service must merge provider-owned stores and preserve provider tags so rows from either CLI open the right provider-specific description/history.
- Layer 2 main instructions are per provider per EPIC-131, but remain editable through the existing in-board Instructions dialog and file-backed storage. Generalize that store in `service.mjs`: Claude keeps the exact `%LOCALAPPDATA%\Persephone\board-data\claude-agent\instructions.md` path and existing default text so saved files remain in use; Codex gets a sibling `instructions-codex.md` and its own default. Do not add instruction settings to the manifest. Keep existing Claude setting ids `claude-executable`, `default-model`, and `default-effort` so current values survive; change their user-visible labels/descriptions to identify the Claude scope. Add Codex executable, default model, and default effort settings only. Continue to treat `cross-board-permission-ceiling` as shared service policy.
- The local instructions dialog already sends `instructions` get/set/reset requests. Generalize these through `service.mjs` and include a provider id in the request; the dialog edits the current view's provider, or the selected engine for a new-session view. BT-050 may move the user-data folder when it renames the board, and must preserve/migrate both instruction files.
- The board guide and live Persephone MCP are available; the guide reports board bridge 1.42.0 and multiline settings require `minBridgeVersion: "1.42.0"`. Keep that minimum unchanged.
- This feature is user-visible. Release accounting belongs to this task: add the terse `## 1.1.0` entry to `boards/claude-agent/WHATS-NEW.md` and set `board-manifest.json` to `1.1.0`. Keep the published display name "Claude Agent" and board id through BT-049; BT-050 owns rebranding/rename.

Separately, lazily start one shared discovery app-server with no MCP config and no token; reuse it for `describe`, cached `model/list`, `thread/list`, history and resume. ## Concerns / Open Questions

- The app-server protocol is experimental and tied to the installed CLI version. The verified planning baseline is `codex-cli 0.163.0`; implementation must recheck and regenerate before coding. Any protocol changes require updating the method/notification map rather than silently relying on prior generated names.
- Dedicated child-per-session is the chosen MCP configuration design because `thread/start`'s free-form `config` was not verified to start per-thread MCP servers. It costs one app-server process per live session; revisiting a shared process requires live proof that per-thread config safely scopes both endpoint URL and bearer-token environment variable.
- The Codex session store is provider-owned. `transcriptFollow` stays false unless an external-writer follow mechanism is demonstrated; does not block listing/history/resume from app-server.
- Approval modes must respect both Codex's sandbox and approval settings and the shared service classifier/ceiling. If generated native policy cannot express the shared mode exactly, the adapter must constrain Codex more tightly and rely on shared approvals; it must never relax the shared decision.
- App-server response shapes and cross-platform JSON-RPC process behavior need live integration verification. No unit test or harness work is authorized; do not add tests.
- No outstanding user decision is required for this plan. Keep BT-050's board rename and `claude-agent:` storage migration out of scope.
